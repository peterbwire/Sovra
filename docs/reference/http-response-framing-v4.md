# Bounded final HTTP response construction

`render_http_response(status, context, headers, body, limits)` is a pure Rust
embedding helper for the initial nonpersistent HTTP profile. It validates and
sizes a complete response before requesting its single output buffer, then emits
exact bytes. It does not send to sockets, read a clock, dispatch handlers or add
network authority. Caller input remains borrowed; no partial output is returned
on error.

## Framing and body rules

The renderer accepts final statuses 200–599. Known statuses have fixed reason
phrases; other accepted codes use `Status`. User-controlled reason phrases,
interim responses and protocol switching are not supported. Output always uses
HTTP/1.1 and a renderer-owned `Connection: close` field.

For ordinary supported requests, the renderer computes Content-Length from the
supplied representation and emits exactly those body bytes. `HttpResponseContext::Head`
uses the same representation length and metadata but emits no body. The caller
must derive that context from the validated request; it is not a handler-provided
framing override. Supplied representation limits still apply to HEAD input.

Statuses 204, 205 and 304 require an empty supplied body; nonempty input refuses
instead of silently discarding it. Statuses 204 and 304 omit Content-Length;
205 emits Content-Length: 0. The optional selected-representation length that
RFC 9110 permits on 304 is intentionally not generated by this initial API.

## Field validation

Names must be ASCII tokens and values must exclude CR, LF, NUL, DEL and other
controls except internal HTAB. Surrounding SP/HTAB refuses rather than being
silently normalized. Empty values and opaque obs-text bytes are preserved.

Content-Length, Transfer-Encoding, Connection, Trailer, Upgrade, Keep-Alive and
Proxy-Connection are reserved case-insensitively. A caller cannot inject framing,
request persistence or protocol switching. Other duplicate names refuse,
including case variants; Set-Cookie is the explicit exception and retains its
separate field lines in input order. No fields are joined implicitly.

This validates generic field syntax and response framing. It does not prove
field-specific/application semantics, such as Content-Range on 206, Allow on 405,
authentication challenges, conditional/cache validators, MIME interpretation or
cookie attributes. Required application metadata remains caller work. Date is
not generated implicitly because this helper has no clock authority.

## Limits and ownership

Hard ceilings are 16 KiB aggregate head, 8 KiB per status/field line, 64 serialized
fields including generated fields, 1 MiB supplied representation, head+body output
bytes and two million logical work units. Callers may only narrow them. Output
and work admission include the actual transmitted body, so HEAD can fit a smaller
output cap. Body input is still independently bounded.

Sizing uses checked arithmetic and fixed stack formatting for status/decimal
length. Validation and work admission precede output allocation/body copying.
`try_reserve_exact` refuses allocation failure. Limits describe serialized/requested
bytes, not allocator overhead, total process memory or a hard execution deadline.
Socket integration must enforce partial-write handling, aggregate I/O limits,
deadlines and connection closure independently.

Tests assert exact binary wire output, HEAD metadata, bodyless statuses, static
status lines, case-insensitive framing refusal, control/CRLF injection refusal,
Set-Cookie order, other duplicate refusal, exact lowered limits, full byte-value
mutations and maximum representation/field boundaries. The pure renderer is now invoked through [HTTP exchanges](http-exchange-v4.md)
from actual Sovra CLI/native handlers under the
[G14 contract](../design/G14_COMPLETION_CONTRACT.md).

## Primary standards reviewed

Reviewed on 2026-11-24:

- [RFC 9112 section 4](https://www.rfc-editor.org/rfc/rfc9112.html#section-4): status-line syntax and reason phrases.
- [RFC 9110 section 5.5](https://www.rfc-editor.org/rfc/rfc9110.html#section-5.5): field-value octets and dangerous control characters.
- [RFC 9110 section 8.6](https://www.rfc-editor.org/rfc/rfc9110.html#section-8.6): generated lengths, HEAD, 204 and 304 restrictions.
- [RFC 9110 section 9.3.2](https://www.rfc-editor.org/rfc/rfc9110.html#section-9.3.2): HEAD without response content.
- [RFC 9110 sections 15.3.5–15.3.6](https://www.rfc-editor.org/rfc/rfc9110.html#section-15.3.5): 204/205 no-content behavior.
- [RFC 9110 section 15.4.5](https://www.rfc-editor.org/rfc/rfc9110.html#section-15.4.5): 304 metadata and no content.

Targeted qualification passes 646 unique Rust tests: eleven response tests,
nine request-parser tests, 26 existing socket/network-host/policy/v3 regressions
and all 600 library tests. Clippy, formatting, exact Rust 1.74.0 and Windows GNU
all-target compilation pass. Windows runtime/HTTP server acceptance is not
established. Logs, the targeted report and primary-standard hashes are retained
under `target/checked-evidence/g14-http-response-framing/`.

[Owned HTTP exchange integration](http-exchange-v4.md) now connects this helper to sockets and real Sovra CLI/native handlers under a bounded one-request policy. Earlier helper-only checkpoint evidence above remains scoped to its original run.
